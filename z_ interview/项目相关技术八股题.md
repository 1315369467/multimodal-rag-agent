# AI Agent 开发岗位技术八股题

> 基于多模态 Agentic RAG 项目，覆盖 RAG、Agent、Embedding、检索、LLM 部署、评测等方向。

---

## 一、RAG 基础

**Q：什么是 RAG，解决了什么问题？**

RAG 全称检索增强生成，核心思路是在 LLM 生成答案之前，先从外部知识库里检索相关内容，把检索结果作为上下文一起喂给模型。

解决的问题主要有三个：一是 LLM 的**知识截止问题**，训练数据有时间限制，RAG 可以接入实时或私有知识；二是**幻觉问题**，生成答案时有了检索到的事实依据，模型编造的概率会降低；三是**私有数据问题**，企业内部文档不可能都拿去微调模型，RAG 提供了一种低成本接入的方式。

---

**Q：Naive RAG 和 Agentic RAG 有什么区别？**

Naive RAG 流程是固定的：用户问题 → 一次检索 → 塞进 prompt → LLM 生成答案，整个过程没有任何自适应能力，检索一次不够也没法补救。

Agentic RAG 把检索、Query 改写、结果判断这些步骤全部**工具化**，由 Agent 根据当前状态自主决定下一步做什么。比如问题很复杂，Agent 会先调 `query_rewrite` 拆成子问题，再分别检索；如果第一次检索结果质量不好，Agent 可以换个角度再检索一轮。本质是把 RAG 从**固定流水线**变成了**自适应决策循环**。

---

**Q：RAG 的主要失败模式有哪些？**

主要有四类：

- **检索不到**：相关文档在库里但没被召回，通常是 embedding 对该领域词汇不敏感，或者 chunk 粒度问题
- **检索到了但没用上**：LLM 拿到了正确片段，但因为上下文太长或者 Lost-in-the-Middle 问题，没有关注到关键信息
- **幻觉**：检索内容和问题关联性弱，LLM 还是按自己的参数记忆生成了答案
- **答非所问**：检索到的内容和问题不完全匹配，LLM 生成了一个听起来合理但实际上不对的答案

---

**Q：RAG 里 chunk 大小怎么选？**

没有一个通用的最优值，需要根据数据和任务来定。

chunk 太小的问题是**语义不完整**，一个知识点被拆成多段，检索时只命中片段，LLM 拿到的上下文缺少前后文，很难给出完整答案。chunk 太大的问题是**向量被稀释**，一个 chunk 里混入太多不相关的内容，语义向量变得模糊，相关性分数反而下降，同时 LLM 的上下文窗口也会更快被填满。

实践中一般**先做消融实验**，用 Recall@K 这类指标对比不同 chunk size 的效果。在我的项目里，1024 token 的 chunk 在 Recall@5 上表现最好。

---

## 二、Embedding 与向量检索

**Q：Embedding 模型和生成模型有什么区别？**

生成模型（比如 GPT、Qwen）是**自回归解码器**，逐 token 生成文本，目标是预测下一个 token。

Embedding 模型通常是**编码器架构**，输入一段文本，输出一个固定维度的稠密向量，这个向量捕捉了文本的语义信息。两个语义相近的句子，它们的向量在空间里距离也近。Embedding 模型训练时一般用对比学习，让相似的文本对向量靠近，不相似的推远。

实际应用里，Embedding 模型负责"表示"，生成模型负责"生成"，RAG 里两者都会用到。

---

**Q：向量相似度常用哪些度量方式，有什么区别？**

主要三种：

- **余弦相似度**：计算两个向量夹角的余弦值，范围 -1 到 1，只关心方向不关心长度，是最常用的，适合文本 embedding
- **点积**：余弦相似度 × 向量模长，如果向量已经归一化了，点积和余弦相似度等价
- **欧氏距离**：直接算两点间距离，值越小越相似，对向量长度敏感

大多数 embedding 模型输出的向量都会做 L2 归一化，所以实际上余弦相似度和点积结果一样。Chroma 默认用余弦相似度。

---

**Q：什么是双编码器，什么是 cross-encoder，分别用在哪？**

**双编码器**：Query 和文档**分别独立编码**，各自得到一个向量，然后算相似度。优点是文档向量可以**离线预计算**，检索时只需要对 query 实时编码，速度非常快，适合大规模召回。缺点是两边编码时互相看不到对方，交互信息缺失，精度有上限。

**Cross-encoder**：把 Query 和文档**拼接在一起**作为一个序列输入模型，模型直接输出一个相关性分数。优点是能捕捉细粒度的语义交互，精度高。缺点是不能预计算，每对 query-doc 都要实时跑一遍模型，计算量大，不适合全库扫描。

实践中通常**组合使用**：双编码器负责从全库召回 top-K 候选，cross-encoder 对候选集精排，这就是"召回-精排"两阶段架构。

---

**Q：什么是稀疏检索，BM25 是怎么工作的？**

稀疏检索基于词汇匹配，每个文档表示为一个高维稀疏向量，绝大多数维度是 0，非零维度对应文档中出现的词。

BM25 是稀疏检索里最经典的算法，在 TF-IDF 的基础上做了改进。核心公式考虑两个因素：一是**词频**（TF），一个词在文档里出现越多，相关性越高，但有饱和处理，避免词频无限叠加；二是**逆文档频率**（IDF），在所有文档里出现越少的词，区分度越高，权重越大。同时还有**文档长度归一化**，避免长文档因为单纯词数多而占优势。

BM25 的优点是对专业术语、缩写、精确关键词匹配效果好；缺点是没有语义理解，"汽车"和"车辆"在它看来是两个完全不同的词。

---

**Q：混合检索为什么要用 RRF，不直接加权平均分数？**

直接加权平均分数有一个根本问题：**稠密检索的余弦相似度和 BM25 的分数量纲完全不同**，余弦值在 0-1 之间，BM25 分数可以很大，没有统一的数值范围，直接加权需要手动归一化，而且不同数据集的最优权重不一样，泛化性差。

RRF 只看**排名**，不看分数，每个文档的得分是 `1/(rank + k)`，k 一般取 60，然后把两路的 RRF 分数加起来。只要排名靠前就得高分，排名靠后就得低分，天然避免了量纲问题，而且在各种数据集上表现都比较稳定，基本不需要调参。

---

**Q：Reranker 加在哪个环节，为什么不直接用 Reranker 全库扫描？**

Reranker 接在混合检索之后，对召回的 top-K 候选（比如 top-10）做精排，最终返回 top-5。

不用 Reranker 全库扫描的原因是**计算量太大**。Reranker 是 cross-encoder，每对 query-doc 都要完整跑一遍模型，假设知识库有 10 万条文档，每次查询要跑 10 万次，延迟完全无法接受。所以必须先用双编码器把候选集压缩到几十条，Reranker 只对这几十条精排，计算量才是可控的。

---

**Q：向量数据库和关系型数据库有什么本质区别？**

关系型数据库存的是结构化数据，查询是精确匹配，比如 `WHERE id = 123`，走的是 B 树索引。

向量数据库存的是高维浮点向量，查询是**近似最近邻搜索**（ANN），找的是在向量空间里最接近 query 向量的 K 个向量，走的是 HNSW、IVF 这类近似索引，因为高维空间里精确暴力搜索的复杂度是 O(n·d)，n 条文档 d 维向量，数据量大了完全撑不住。

常见的向量数据库有 Chroma（轻量本地）、Milvus（分布式生产级）、Pinecone（云托管）、Qdrant 等。

## 三、LangChain 与 Agent 框架

**Q：LangChain 的核心抽象有哪些？**

主要几个核心抽象：

- **LLM / ChatModel**：对各家模型 API 的统一封装，换模型只需改一行
- **Prompt Template**：管理提示词模板，支持变量插值
- **Chain**：把多个组件串联成流水线，比如 `prompt → llm → parser`
- **Document / Retriever**：文档和检索器的统一接口，支持各种向量库
- **Tool**：把函数包装成 Agent 可以调用的工具，带名称和描述
- **Memory**：多轮对话的历史管理

LangGraph 是 LangChain 生态里的 Agent 编排框架，把 Agent 的执行过程建模成有向图，状态显式管理，比 AgentExecutor 更灵活可控。

---

**Q：ReAct 框架是什么，为什么叫 ReAct？**

ReAct 全称 Reasoning + Acting，思路是让 LLM **交替进行推理和行动**。

每一轮 LLM 先输出 `Thought`（我需要做什么，为什么），然后输出 `Action`（调用哪个工具，参数是什么），收到工具返回的 `Observation` 后再继续推理，直到 LLM 认为信息足够了，输出最终答案。

和直接调工具相比，ReAct 的优点是 LLM 的推理过程是显式的，可以看到它为什么这么决策，也更容易 debug。缺点是每轮都要输出 Thought，增加了 token 消耗和延迟。

---

**Q：LangGraph 和 LangChain AgentExecutor 有什么区别？**

AgentExecutor 是一个黑盒循环，内部状态不透明，自定义控制流很麻烦，流式输出也难实现。

LangGraph 把 Agent 执行过程建模成**有向图**，每个节点是一个处理步骤（比如"调用 LLM"、"执行工具"），边代表状态转移条件，整个执行状态是显式的 State 对象。好处有三个：

1. **流式天然支持**：每个节点执行完可以立刻把中间结果推出去，实现 SSE 流式响应
2. **状态可控**：出错了可以从某个节点重试，不用整个流程重跑
3. **条件分支灵活**：可以根据 LLM 的输出决定走哪条边，实现复杂的控制流

---

**Q：Agent 里的工具描述为什么很重要？**

工具描述是 LLM 决策"要不要调这个工具、什么时候调"的唯一依据。LLM 在选工具时本质上是在做文本匹配和推理，如果描述太模糊，LLM 就判断不了该调哪个工具，甚至直接不调工具、自己编答案。

好的工具描述需要明确三点：**这个工具做什么、什么情况下用它、输入输出格式是什么**。比如 `image_search` 的描述应该明确写"当问题涉及图表、图片、可视化内容时调用"，而不是笼统地写"搜索图片"。

在我的项目里，工具描述优化之后 Agent 的工具调用准确率有明显提升，这也说明**Prompt 工程在 Agent 开发里和模型能力同等重要**。

---

**Q：多轮对话里 Agent 怎么维护上下文？**

主要有两种方式：

**方式一：完整历史**：把所有历史对话都塞进 prompt，最简单，但随着轮数增加，context 越来越长，最终会超出模型的上下文窗口限制，而且越长越贵。

**方式二：摘要压缩**：超过一定长度后，用 LLM 把早期的对话历史压缩成摘要，只保留摘要 + 最近几轮原始对话，控制总长度。

实际工程里还要考虑：history 里只放 user/assistant 的对话，工具调用的中间步骤通常不放进历史，不然 context 会膨胀得很快。

---

**Q：如果 Agent 陷入死循环怎么处理？**

设置**最大迭代次数**是最基础的保护，LangGraph 里可以在图的边上加条件，超过 N 步就强制终止并返回当前最好的结果。

另外可以加**重复检测**，如果连续两轮调用了完全相同的工具和参数，说明 Agent 卡住了，直接中断。

更好的做法是在 prompt 里明确告诉 Agent："如果两轮检索后还没找到足够信息，直接基于现有内容回答并说明不确定"，从根源上减少无效循环。

---

## 四、文档解析与分块

**Q：为什么要用 MinerU 而不是直接用 PyPDF2 这类库解析 PDF？**

PyPDF2 这类库只是提取 PDF 的文本层，对于**数字原生 PDF**（直接从 Word 导出的那种）基本够用。但企业文档里大量是扫描件，或者有复杂的多栏排版、嵌入式图表、公式，这类文档里根本没有文本层，PyPDF2 提取出来要么是乱码要么是空的。

MinerU 的思路是先做**布局分析**，识别页面上每个区域是文本、表格还是图片，然后对文本区域做 OCR，最后按阅读顺序重组成结构化 Markdown。这样不管是扫描件还是复杂排版，输出格式都是统一的，后续处理就方便多了。

---

**Q：结构感知分块和普通的递归切分相比，优势在哪？**

普通递归切分（比如 LangChain 的 `RecursiveCharacterTextSplitter`）只看文本，按字符数切，切割点可能落在表格中间、段落中间，完全不管文档结构。

结构感知分块的输入是带类型标注的 `ParsedBlock` 列表，分块逻辑针对不同块类型有不同处理：

- **表格、图注**：作为原子块整体输出，绝不截断
- **标题**：不单独输出，而是作为上下文前缀附加到后续每个 chunk，每个 chunk 都知道自己属于哪个章节
- **普通文本**：才走滚动缓冲区 + 超限切分的逻辑

这种设计的核心价值是：**检索到的每个 chunk 语义是完整的**，LLM 拿到的上下文不会是半张表或者缺少章节信息的孤立段落。

---

**Q：chunk overlap 是什么，什么策略需要用，什么策略不需要？**

Chunk overlap 是相邻 chunk 之间的重叠内容，目的是避免切割点恰好落在一句话中间导致语义断裂。比如 overlap 设 100 个 token，下一个 chunk 会复制上一个 chunk 末尾的 100 个 token 作为开头。

并不是所有策略都需要 overlap：
- 按**句子**切的不需要，句子本身就是完整的语义单元
- 按**段落**切的不需要，段落边界是作者有意划定的语义边界
- 按**Markdown 标题**切的不需要，标题已经作为 context 前缀提供了上下文锚点
- **递归切分**和**结构感知切分**需要，因为切割点可能落在非边界位置，overlap 能弥补跨块的语义断层

---

## 五、多模态与跨模态检索

**Q：什么是多模态 Embedding，和普通文本 Embedding 有什么区别？**

普通文本 Embedding 只能把文本映射到向量空间，不同模态的内容在各自的向量空间里，没法直接比较。

多模态 Embedding（比如 Qwen3-VL-Embedding）的目标是把**文本和图片映射到同一个向量空间**，语义相近的文本和图片在空间里距离也近。这样就能实现"以文搜图"——把查询文本 embed 出一个向量，直接和图片的向量算余弦相似度，找到语义最相关的图片。

这类模型通常用**对比学习**训练，用大量文本-图片配对数据，让对应的文本和图片向量拉近，不对应的推远。

---

**Q：为什么图像向量和文本向量不能混在一起做 RRF 融合？**

RRF 融合的前提是两路检索的排名有参考意义，反映的是"和 query 的相关程度"。

图文混合的问题是：**文本条目的数量远多于图片**，即使某张图片和 query 非常相关，在稠密向量余弦召回里，它的相关性分数可能在同等语义的文本里只算中等水平，排名会很靠后。RRF 融合后，被大量文本结果稀释，图片几乎排不进 top-5。

测试验证了这一点，混合之后图片召回率很低。正确的做法是**两条路完全独立**，文本走自己的检索链路，图片走自己的，由 Agent 根据问题语义决定调哪个。

---

**Q：Qwen3-VL-Embedding 用的是什么 pooling 方式，为什么？**

用的是 **last token pooling**，取序列里最后一个被 attention mask 覆盖到的 token 的 hidden state 作为整个序列的表示。

原因是 Qwen3-VL-Embedding 的基座是**因果语言模型**（Decoder-only），不是双向 Encoder。因果模型里每个 token 只能看到自己左边的内容，所以只有最后一个 token 的 hidden state 汇聚了整个序列的信息，做 mean pooling 是没意义的（前面的 token 没见过后面的内容）。这和 BERT 系模型用 `[CLS]` token 或者 mean pooling 是不一样的逻辑。

---

## 六、LLM 推理与部署

**Q：vLLM 是什么，解决了什么问题？**

vLLM 是一个高性能的 LLM 推理框架，核心创新是 **PagedAttention**。

LLM 推理时需要缓存每一层的 KV（Key-Value），叫 KV cache。传统实现里 KV cache 是连续分配的内存块，但每个请求的序列长度不同，内存碎片化严重，GPU 利用率低。PagedAttention 借鉴操作系统的分页内存管理思想，把 KV cache 切成固定大小的小块按需分配，大幅减少内存碎片，让同一个 GPU 能同时处理更多并发请求，吞吐量提升显著。

在我的项目里，主 LLM 支持通过 `LLM_MODE=local` + `LOCAL_LLM_BASE_URL` 切换到本地 vLLM 推理服务，接口兼容 OpenAI API 格式。

---

**Q：LLM 推理的 prefill 和 decode 阶段有什么区别？**

**Prefill 阶段**：处理整个输入序列（prompt），并行计算所有 token 的 KV cache，是计算密集型（compute-bound），GPU 利用率高，延迟主要和输入长度成正比。

**Decode 阶段**：逐 token 自回归生成，每次只生成一个新 token，需要读取所有之前 token 的 KV cache，是内存带宽密集型（memory-bound），GPU 的计算单元大部分时间在等内存读写。

这就是为什么 LLM 的**首 token 延迟**（prefill）和**生成速度**（decode throughput）是两个独立的优化维度，不能混为一谈。

---

**Q：什么是量化，INT8 和 FP16 有什么区别？**

量化是把模型权重从高精度浮点数压缩成低位整数来存储和计算，减少显存占用和提升推理速度。

- **FP32**：32位浮点，训练时常用，显存消耗最大
- **FP16 / BF16**：16位浮点，推理时常用，显存减半，精度损失很小，是目前主流部署精度
- **INT8**：8位整数，显存进一步减半，需要做量化校准，会有一定精度损失，但对大多数任务影响可接受
- **INT4**：4位整数，显存减到 FP32 的 1/8，精度损失更大，适合显存非常紧张的场景

常见的量化方案有 GPTQ（训练后量化）、AWQ（激活感知量化）等。

---

**Q：什么是 KV cache，它的作用是什么？**

KV cache 是 Transformer 推理时的优化技术。自注意力机制里每个 token 都需要和前面所有 token 做 attention，计算时需要用到前面所有 token 的 Key 和 Value 矩阵。

如果每次生成新 token 都重新计算所有历史 token 的 K、V，计算量随序列长度平方增长。KV cache 的做法是**把已经算好的 K、V 缓存起来**，生成新 token 时只需要计算新 token 的 K、V，再和缓存的历史 K、V 拼接做 attention，把计算复杂度从 O(n²) 降到 O(n)。

代价是**显存消耗**，序列越长，KV cache 占用的显存越多，这也是长上下文推理显存压力大的根本原因。

---

**Q：temperature 和 top-p 是什么，怎么影响生成结果？**

这两个都是控制 LLM 生成多样性的参数，作用在 softmax 之后的概率分布上。

**Temperature**：把 logits 除以 temperature 再做 softmax。temperature < 1 让概率分布更尖锐，高概率的 token 更容易被选中，生成更保守确定；temperature > 1 让分布更平坦，低概率 token 也有机会被选中，生成更随机多样；temperature = 0 等价于贪心解码，每次选概率最高的。

**Top-p（核采样）**：每次从概率最高的若干个 token 里采样，这些 token 的累积概率加起来达到 p。比如 top-p=0.9，从累积概率前 90% 的 token 集合里随机采样，动态过滤掉尾部低质量 token。

在问答类任务里通常 temperature 设低一点（0.1-0.3），要的是准确而不是创意。

## 七、评测与指标

**Q：Recall@K 和 MRR@K 分别衡量什么，有什么区别？**

**Recall@K**：在返回的前 K 个结果里，有多少比例的问题找到了正确答案。比如 Recall@5=95% 意思是 95% 的问题，正确答案出现在检索结果的前 5 条里。衡量的是**覆盖率**，只关心答案在不在前 K 里，不关心排第几。

**MRR@K（平均倒数排名）**：对每个问题，正确答案在前 K 里排第几名，取倒数（第 1 名得 1 分，第 2 名得 0.5 分，第 3 名得 0.33 分……），然后所有问题取平均。衡量的是**排名质量**，正确答案越靠前，MRR 越高。

两个指标侧重不同：提升召回阶段主要看 Recall@K，提升精排阶段主要看 MRR@K 和 NDCG。我的项目里加 Reranker 之后，Recall@5 变化不大（95% → 95.9%），但 **MRR@1 从 0.76 提升到 0.87**，说明 Reranker 主要贡献是把正确答案排到更靠前的位置。

---

**Q：怎么构建 RAG 系统的评测数据集？**

主要有两种方式：

**人工标注**：让领域专家基于文档写问答对，质量最高但成本极大。

**LLM 自动生成**：把文档片段喂给 LLM，让它根据每个片段生成问题和答案，同时记录答案的来源文档和位置。成本低，可以快速生成大量数据。缺点是可能会有重复问题或者 LLM 生成的问题过于简单，需要后处理去重和过滤。

我的项目里用的是 LLM 自动生成 + 去重的方式，生成了 173 条问答对，足够做方法对比评估。

---

**Q：怎么评估生成答案的质量，不只是检索质量？**

检索评估用 Recall、MRR 这类有标准答案的指标。

生成质量的评估更难，因为同一个问题可以有多种正确表达。常见方案：

- **ROUGE / BLEU**：和参考答案做 n-gram 重叠度计算，简单快速，但对语义等价的不同表达不公平
- **LLM-as-Judge**：让一个强模型（比如 GPT-4）对生成答案打分，评估准确性、完整性、流畅度，更贴近人类判断，但成本高，也有位置偏见等问题
- **人工评估**：最可靠但最贵，通常用于最终验收

RAG 场景里还有一个专门的评估框架叫 **RAGAS**，同时评估检索质量（context recall、context precision）和生成质量（faithfulness、answer relevancy）。

## 八、工程与系统设计

**Q：RAG 系统的整体架构一般怎么设计？**

通常分两条链路：

**离线链路（文档入库）**：文档 → 解析 → 分块 → embedding → 写入向量库。这条链路是异步的，可以批量处理。

**在线链路（查询服务）**：用户查询 → Query 理解/改写 → 检索 → 精排 → 组装 prompt → LLM 生成 → 返回答案。这条链路是同步的，对延迟敏感。

工程上通常用 FastAPI 暴露 REST 接口，向量库和 LLM 服务作为独立模块，通过环境变量配置。流式输出用 SSE（Server-Sent Events）推送，前端可以实时显示生成过程。

---

**Q：SSE 和 WebSocket 有什么区别，RAG 的流式输出为什么用 SSE？**

**WebSocket** 是全双工通信，客户端和服务端都可以随时发消息，适合实时聊天、协作编辑这类需要双向通信的场景。

**SSE（Server-Sent Events）** 是单向的，只能服务端向客户端推送数据，基于 HTTP 长连接，客户端用 `EventSource` API 监听。

RAG 流式输出用 SSE 的原因：LLM 生成是服务端向客户端单向推送 token，不需要双向通信。SSE 更轻量，基于标准 HTTP，不需要额外握手，对负载均衡和反向代理更友好，实现也更简单。

---

**Q：知识库更新了一篇文档，怎么处理？**

需要处理三件事：

1. **删除旧版本**：在向量库里找到该文档对应的所有 chunk（通过 metadata 里的 source 字段过滤），全部删除
2. **重新解析和分块**：对新版文档走一遍完整的解析 → 分块 → embedding 流程
3. **写入新 chunk**：把新 chunk 写入向量库，同时更新 BM25 稀疏索引

这就是为什么每个 chunk 的 metadata 里要保存 `source`（来源文件名），方便定向删除和更新，不需要重建整个向量库。

---

**Q：RAG 系统如何保证答案可追溯，避免 LLM 乱编？**

主要靠两点：

**检索来源透传**：每个检索到的 chunk 都带着 metadata（来源文件、页码、章节），组装 prompt 时把来源信息也带上，让 LLM 在生成答案时能引用来源。返回给用户时同时返回 `sources` 字段，用户可以点击验证原文。

**Prompt 约束**：在系统提示里明确告诉 LLM："只根据提供的参考资料回答，如果参考资料里没有相关信息，直接说不知道，不要编造"。LLM 遵从这个指令的概率取决于模型能力，Qwen、GPT-4 这类强模型通常遵从得比较好。

---

**Q：如果知识库里没有相关内容，RAG 系统应该怎么处理？**

有几种策略：

1. **直接告知**：Prompt 里要求 LLM 在检索内容不相关时回复"知识库里没有相关信息"，不要强行回答
2. **设置相关性阈值**：检索结果的相似度分数低于某个阈值时，认为没有相关内容，跳过生成直接返回"未找到"
3. **Fallback 到网络搜索**：我的项目里挂了 `web_search` 工具，Agent 在知识库检索无果时可以自主调用网络搜索补充信息
4. **混合策略**：先检索知识库，知识库有就用知识库，没有就 fallback 到 LLM 参数记忆或网络搜索，并在答案里标明来源

---
