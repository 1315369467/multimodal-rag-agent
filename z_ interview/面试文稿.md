# 面试文稿：多模态 Agentic RAG 知识库问答系统

---

## 一、项目自我介绍（约 1.5 分钟）

> 开场时面试官问"介绍一下你最近做的项目"，用这段。

好的，我最近做了一个**多模态的 Agentic RAG 知识库问答系统**，主要解决的问题是：企业里有大量复杂文档，比如扫描件、带表格和公式的 PDF，传统 RAG 系统在解析这类文档时很容易**把表格截断、把图片丢掉**，导致检索质量很差。

我这个系统从文档解析到问答形成了一个完整链路。整体分三块说：

**第一块是文档解析。** 我用 **MinerU** 做 布局识别 和 OCR，把各类复杂文档统一转成结构化 Markdown 格式，然后自己实现了一个**结构感知的分块器**——把表格、图注这些不能被截断的元素作为**原子块**单独输出，标题不拆开而是作为**上下文前缀**附加到后续每个 chunk 里，这样检索时每个片段都知道自己属于哪个章节。

**第二块是检索。** 我用了**混合检索**，稠密向量走 **Qwen3-Embedding**，稀疏走 **BM25**，然后用 **RRF** 做无参数融合，再接一个 **Qwen3-Reranker** 精排。另外我单独维护了一个**图像向量库**，用 **Qwen3-VL-Embedding** 把文档里的图片也向量化，支持"以文搜图"。

**第三块是 Agent 调度。** 我用 **LangGraph** 实现了 **ReAct Agent**，把 Query 重写、文本检索、图像检索这些模块都**工具化**，Agent 根据问题自主决定调哪些工具、调几轮。前端用 Streamlit 做了可视化，支持**流式展示**每一步工具调用的过程。

评测结果上，对比朴素 RAG，**Recall@5 从 82% 提升到了 95%，MRR@5 从 0.75 提升到了 0.91**，单次检索延迟大概在 **250 毫秒**左右。

## 二、深度技术问答

### Q1：你说的结构感知分块，具体是怎么做的？

我实现了一个 `StructureAwareChunker`，输入是解析后的 `ParsedBlock` 列表，每个 block 有类型标注，比如 **HEADER、TEXT、TABLE、FIGURE**。

处理逻辑是这样的：

- 遇到 **HEADER**，不输出，而是把标题文本存起来作为**"章节上下文"**，附加到后续每一个 chunk 的开头。
- 遇到 **TABLE 或者 FIGURE**，直接作为**原子块整体输出**，不管它多大都不截断。
- 遇到普通 **TEXT**，放进一个**滚动缓冲区**，超过 chunk_size 了就输出，然后从上一个 chunk 末尾取一小段作为**重叠**，保证跨块的上下文连贯性。

这样做有两个好处：一是**每个 chunk 都带着自己属于哪个章节**，检索时不会出现"知道答案但不知道上下文是什么"的情况；二是**表格绝对不会被截成半张表**，图注也不会和图片分离。

---

### Q2：混合检索里 RRF 是怎么工作的，为什么不用分数加权？

**RRF 的思路**：把稠密检索和稀疏检索各自的结果按排名打分，每个文档的得分是 `1 / (rank + k)`，然后两路加起来排序。

选 **RRF 不用分数加权**，主要有两个原因：

1. **量纲不同**：稠密向量的余弦相似度和 BM25 的分数量纲完全不同，没办法直接加权，需要手动调参，而且对不同数据集的鲁棒性很差。**RRF 只看排名**，天然规避了这个问题。
2. **实验验证**：在我的数据集上做了对比实验，RRF 效果比线性加权稳定。

---

### Q3：Reranker 和初次检索有什么区别，为什么要多一步？

- **初次检索（双编码器）**：Query 和文档**分别独立编码**，靠向量相似度匹配，速度快但精度有上限，因为**两边的交互信息是缺失的**。

- **Reranker（cross-encoder）**：把 Query 和候选文档**拼在一起输入模型**，让模型直接输出相关性分数，能捕捉到**细粒度的语义交互**。缺点是不能离线预计算，所以只能对初检的 **top-10 再精排到 top-5**。

评测数据：开启 Reranker 后，**Recall@1 从 76.3% 提升到 86.7%，MRR@1 从 0.76 提升到 0.87**，提升非常明显。

---

### Q4：图像检索那块，为什么要维护两个独立的向量库，不直接混在一起？

我最开始的方案就是混在一起，查询时同时返回文本片段和图片。但实际测试之后发现一个问题：**绝大多数问题其实根本不需要图片**，用户问的都是文字性的内容，结果每次回答都夹着一堆图片，**大部分时候图像结果是多余的、甚至是干扰性的**。

所以我把文本和图像**拆成两个独立的检索路径**：

- **文本库**：走稠密+稀疏+RRF+rerank 这一套，专注文本问答
- **图像库**：单独一个集合，只有明确需要图片时才调

关键在于**让 Agent 来决策**：`knowledge_base_search` 和 `image_search` 是两个独立工具，LLM 根据问题语义自己判断要不要调图像检索。用户问"这张图展示了什么"或者"有没有架构图"，Agent 才会去调 `image_search`；普通问答就只走文本路径。这样**图片只在真正有用的时候出现**，不会造成干扰。

---

### Q5：Agentic RAG 相比 Naive RAG，最核心的提升在哪？

**Naive RAG** 就是"一次检索，直接生成"，整个流程是固定的，没有任何自适应能力。

**Agentic RAG 的核心提升有三点：**

1. **Query 重写**：用户的原始问题往往很口语化、有歧义，`query_rewrite` 工具可以把一个复杂问题**改写成多个更精确的子查询**，每个子查询再分别检索，然后合并去重，命中率会明显提升。

2. **多轮检索**：如果第一轮检索的结果不够，**Agent 可以根据已有信息决定换个角度再检索一次**，在回答需要综合多个文档片段的问题时特别有用。

3. **工具扩展性**：除了检索工具，还挂了**网络搜索、表格分析、图像描述、计算器**这些 skill，知识库答不了的问题可以 fallback 到网络，遇到数学计算**不让 LLM 口算**，准确性更高。

---

### Q6：你的评测数据集是怎么来的？

评测数据集用 **LLM 自动生成**，`generate_eval_dataset.py` 脚本的做法是：把知识库里的文档片段喂给 LLM，让它根据每个片段**生成问答对**，同时记录答案对应的 source 文件和页码。

生成完之后还有一步**去重**，`dedup_dataset.py` 会过滤掉语义重复的问题，避免评测偏向高频内容。最终用了 **173 条问答对**做在线评估。

评估脚本支持：
- **离线模式**：只跑 BM25，不需要 API
- **在线模式**：走完整的 dense+sparse+rerank 流水线
- **消融实验**：单独跑只有稠密或只有稀疏的配置，量化每个组件的贡献

---

### Q7：项目里 LLM 和 Embedding 模型的部署方式是怎么设计的？

通过**环境变量控制本地/API 两种模式切换**，不需要改代码：

| 组件 | 本地模式 | API 模式 | 切换方式 |
|------|---------|---------|---------|
| LLM | qwen3-8b（vLLM） | qwen3-plus（DashScope） | `LLM_MODE=local/api` |
| 文本 Embedding | Qwen3-Embedding-0.6B | text-embedding-v4 | `EMBEDDING_MODE=local/api` |
| Reranker | Qwen3-Reranker-0.6B | qwen3-rerank | `RERANKER_MODE=local/api` |
| 图像 Embedding | Qwen3-VL-Embedding-2B | 无 API，**固定本地** | — |

设计的好处：**本地 GPU 充足时全部本地跑，隐私安全；资源不足时切 API，不用改代码。**

## 三、容易被追问的坑，提前准备

### chunk size 你怎么确定选 1024？

做了消融实验，对比了 256、512、1024 这几个配置，在我的数据集上 **1024 的 Recall@5 最高**。**chunk 太小**的话一个完整的知识点被截成多段，检索时容易只命中片段；**chunk 太大**的话噪声多，精排也更难。

---

### LangGraph 和直接用 LangChain AgentExecutor 有什么区别，为什么选 LangGraph？

**LangGraph** 把 Agent 的执行过程建模成**有向图**，每个节点是一个状态，状态之间有明确的转移条件：

- **流式输出自然**：每个节点执行完可以立刻推送 SSE 事件
- **状态可控**：出错了可以回退到某个节点重试，而不是整个链重跑

**LangChain AgentExecutor** 是黑盒循环，**状态不透明**，定制流式输出也比较麻烦。

---

### 延迟 250ms 是怎么测出来的，包含 Reranker 吗？

这个是**在线模式下混合检索的检索阶段延迟**，包含稠密+稀疏+RRF融合，**不含 Reranker**。加上 Reranker 之后延迟会增加，大概会**多出 100-200ms**。端到端的问答延迟还要加上 LLM 生成时间，那个变化比较大，主要看问题复杂度和 API 响应速度。

---

### 这个系统在实际企业场景里有哪些局限性？

1. **文档解析依赖 MinerU**，对特别复杂的扫描件或者非标准排版还是会有识别错误，这是上游问题
2. **图像检索**目前只支持"以文搜图"，图片的深度理解靠 `image_describer` skill 临时调 VL 模型，没有做成索引
3. **Chroma 是单机向量库**，数据量上去之后需要换成分布式方案比如 Milvus
4. **Agent 决策取决于 LLM 能力**，如果模型能力弱，工具调用的准确性会下降

## 四、项目难点 / 亮点 / 踩坑三连问

### Q：这个项目最难的地方是什么？

难点主要集中在两块：

**第一块是如何在检索质量和延迟之间找到平衡点。**

Reranker 是整个检索链路里延迟最高的环节，因为它是 cross-encoder，每对 query-doc 都要过一次模型，没法并行。但如果不加 Reranker，只靠 RRF 融合，Recall@1 只有 76%，对于需要精准定位的问答场景是不够的。

这里的核心权衡是：**召回阶段用双编码器打宽，精排阶段用 cross-encoder打准**。我的做法是初检阶段放大候选集到 top-10，Reranker 只对这 10 条精排，最终返回 top-5。这样 Reranker 的计算量是可控的，加入之后 Recall@1 从 76% 提升到 87%，MRR@1 从 0.76 提升到 0.87，延迟增加在可接受范围内。这个"**召回打宽、精排打准**"的两阶段思路也是工业界主流做法。

**第二块是多模态检索的架构设计决策。**

最难的不是写代码，而是**想清楚图文应该怎么组织**。一开始很自然地想把文本和图片放进同一个向量库，用统一的相似度排序。但实际测下来发现不行——文本条目数量远多于图片，即使图片很相关，混合排序后也会被大量文本稀释，排到很靠后。

最终的设计是**维护两个完全独立的集合，文本和图像走不同的 embedding 模型，检索路径完全分开，由 Agent 根据问题语义决定调哪条路**。这个决策背后的核心认知是：**多模态不等于混在一起，模态间的分布差异决定了需要独立建模**。

---

### Q：相比其他 RAG 方案，你这个项目有什么特别之处？

我觉得主要有三点和常见方案不一样：

**第一是分块不是无脑切，而是结构感知的。**

大多数 RAG 项目直接用 `RecursiveCharacterTextSplitter` 按字符数切，根本不管文档结构。我的方案里 TABLE 和 FIGURE 是**原子块**，不管多大都不截断；HEADER 不单独输出，而是作为上下文前缀附加到后续每个 chunk，让每个 chunk 都知道自己在文档的哪个章节。消融实验数据可以说明这一点：`fixed` 策略的 Recall@5 只有 62.5%，而我的 `semantic` 策略达到了 95%，提升非常显著。

**第二是图文两条完全独立的检索路径，由 Agent 来调度。**

常见的多模态 RAG 方案要么只做文本检索，要么把图片和文本强行混在一个向量空间里。我实测之后发现混在一起图片几乎永远排不到前面，因为文本条目数量远多于图片。所以我**维护了两个独立的 Chroma 集合**，文本走稠密+稀疏+RRF+rerank，图片走 VL 向量直接余弦召回，由 LangGraph Agent 根据问题语义自己决定调哪条路径。

**第三是 Embedding 和 Reranker 的本地/API 双模式切换。**

这个在实际使用里很实用——本地 GPU 充足的时候全链路本地跑，隐私安全；GPU 不够或者想快速演示的时候通过环境变量切成 DashScope API，**不需要改任何代码**。VL Embedding 因为没有官方 API，是唯一一个固定本地推理的组件。

---

### Q：开发过程中遇到过什么困难，怎么解决的？

**一是检索召回率上不去的问题。**

最开始只用稠密检索，Recall@5 大概在 70% 出头，瓶颈在于向量检索对专业术语、缩写这类词汇不敏感，比如问"ROE"，embedding 出来的向量和文档里的"净资产收益率"语义距离比较远，召回不到。引入 BM25 稀疏检索之后，关键词精确匹配补上了这块缺口，再用 RRF 融合，Recall@5 提升到了 94.8%，提升非常明显。所以**稠密和稀疏检索是互补关系**，不是谁替代谁。

**二是 chunk 粒度和检索精度的权衡。**

chunk 切太小，一个完整的知识点被拆散，检索时只命中片段，LLM 拿到的上下文不完整，答案质量差；切太大，一个 chunk 里混入太多不相关内容，向量被"稀释"，相关性分数反而下降。我做了消融实验，对比了固定大小、句子、段落、Markdown 标题、递归切分和结构感知切分六种策略。结果是**结构感知切分效果最好**，核心原因是它保证了表格这种高密度信息不被截断，同时标题作为上下文前缀能让每个 chunk 在语义上更完整。

**三是 Agent 工具调用的稳定性问题。**

早期测试发现 Agent 有时候对明显需要检索的问题直接生成答案，直接"幻觉"了。根本原因是**工具描述写得太模糊**，LLM 没有足够的信号判断该不该调工具。解决方案是把每个工具的触发条件写得非常明确和具体：`query_rewrite` 明确标注"问题包含多个子问题或语义模糊时调用"，`image_search` 明确标注"问题涉及图表、图片、可视化内容时调用"。工具描述其实就是给 LLM 的 prompt，**写好工具描述比调模型参数更有效**，这是做 Agent 开发很重要的一个体会。
